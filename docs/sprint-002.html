Sprint 2: Juice & Game Feel

Epic: EPIC-002 Goal: Make every action feel satisfying Status: Planned

Every mechanic from Sprint 1 works but feels flat. This sprint adds screen shake, particles, sound, and visual polish so hitting an enemy, getting hit, or clearing a floor feels like something.

Tasks

SC-201 — Screen shake

  • Camera shake on player damage (medium intensity)
  • Camera shake on enemy death (low intensity)
  • Camera shake on floor transition (brief, directional)
  • Configurable intensity + duration per event
Acceptance: Taking damage visibly shakes the screen. Enemy deaths cause a subtle rumble.

SC-202 — Hit flash

  • Enemy sprite turns white for 80ms when hit
  • Player sprite flashes red briefly on damage
  • Invulnerability period has distinct visual (pulsing alpha preserved from Sprint 1)
Acceptance: Every hit produces a visible feedback flash on the target.

SC-203 — Death particles

  • Enemy death spawns 8-12 small particles in enemy color
  • Particles scatter outward with random velocity + gravity
  • Particles fade out over 400-600ms
  • Reusable particle emitter utility
Acceptance: Killing an enemy produces a satisfying particle burst. Different enemy colors produce different bursts.

SC-204 — Floor transition animation

  • Walking onto exit tile triggers a fade-to-black (300ms)
  • "Floor N" text appears with scale-up animation mid-fade
  • Fade back in to new floor layout
  • Player briefly invulnerable on arrival
Acceptance: Floor transitions feel like a game event, not an instant cut.

SC-205 — Sound effects

  • Generate or source retro sound effects (Web Audio API synthesis)
  • Sounds required: player shoot, enemy hit, enemy death, player hit, player death, floor clear, pickup
  • Use Phaser's built-in audio or Web Audio oscillator-based synthesis
  • Volume control placeholder (global setting, defaults to 0.5)
Acceptance: Every action with a visual effect also has an audio cue. Sound can be muted.

SC-206 — Damage numbers

  • Floating text appears at enemy position when hit
  • Number = damage dealt, colored white
  • Floats upward and fades over 600ms
  • Small upward velocity + random horizontal offset
Acceptance: Each hit shows a floating damage number that fades out.

SC-207 — Sprite texture generation

  • Render adversary sprite recipes to actual canvas textures at boot time
  • Use Phaser.GameObjects.RenderTexture or canvas texture generation
  • Replace colored rectangles with generated textures for enemies
  • Player gets a simple ship/character texture too
Acceptance: Enemies render as pixel-art sprites from their recipe instead of solid rectangles.

SC-208 — Projectile trails

  • Each projectile leaves a short fading trail (3-5 trailing circles)
  • Trail color matches projectile color, alpha decreases with age
  • Trail disappears when projectile is destroyed or off-screen
Acceptance: Projectiles have a visible motion trail behind them.

Definition of Done

  1. Every task AC met and manually play-tested
  2. npm run build passes with 0 errors
  3. npm run lint passes with 0 errors, 0 warnings
  4. No regression in Sprint 1 gameplay (core loop still works)
  5. Sprint review written to docs/sprint-002-review.html

Architecture Notes

  • Particle effects: create a game/systems/Particles.ts utility class
  • Screen shake: use this.cameras.main.shake(duration, intensity)
  • Sound: create game/systems/Audio.ts using Web Audio API oscillators (no asset files needed)
  • Sprite textures: generate Phaser.Textures from canvas at boot time in BootScene
  • Damage numbers: lightweight Phaser.GameObjects.Text with tween animation
  • Projectile trails: array of circles parented to projectile, recycled/removed as they fade

Dependencies

  • SC-207 (sprite textures) depends on game/generation/sprites.ts from Sprint 1
  • SC-203 (death particles) and SC-206 (damage numbers) both depend on enemy hit detection from CombatSystem
  • SC-204 (floor transition) depends on DungeonScene's nextFloor flow from Sprint 1
  • All other tasks are independent and can be parallelized
